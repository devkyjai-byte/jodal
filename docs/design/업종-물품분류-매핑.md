# 업종-물품분류 매핑 설계 문서

## 결론 먼저

업체 프로필이 저장하고 나라장터 공고와 조인할 값은 **나라장터 물품분류번호(UNSPSC 기반, 대분류-중분류-소분류-품명분류 2자리×4단계 = 최대 8자리) 계열**이다. 국세청 사업자등록증의 업태·종목이나 나라장터 참가자격 업종코드(4자리류)는 조인 키로 쓰지 않는다 — CONTEXT.md **D-06**이 이미 이렇게 결정했고, 이 문서는 그 결정을 실제 코드 조회로 뒷받침한다.

`REQUIREMENTS.md`의 PROF-01 요구사항 문구는 "업체는 업종코드(업태·품목)를 등록할 수 있다"라고 되어 있지만, 실제로 DB에 저장되고 공고와 조인되는 값은 물품분류번호 계열이다 — **PROF-01의 "업종코드"라는 단어와 실제 저장 값(물품분류번호)이 다르다는 용어 불일치**를 Phase 2 planner가 반드시 인지해야 한다. 이 불일치를 인지하지 못하고 문구 그대로 업태·종목이나 참가자격 업종코드를 저장하면, 공고 데이터와 조인할 방법이 없어져 매칭 엔진(MATCH-01)이 처음부터 동작하지 않는다(RESEARCH.md Pitfall 1).

이번 조회에서 목표 업종 4개 중 3개(정보통신·소프트웨어개발/사무용품/인쇄·출판)는 실제 나라장터 공식 물품 목록 타이틀을 검색엔진 색인을 통해 직접 확인했고, 1개(시설관리)는 확인하지 못해 `[미확인]`으로 남겼다 — 아래 §목표 업종 매핑표, §미확인 항목과 확인 방법 참고.

**참고 — 세부 자릿수 보정:** 나라장터 실무에서는 "물품분류번호(8자리)"에 "물품식별번호(추가 2자리)"를 더한 **10자리 "물품목록번호"**를 실제 계약·공고에 사용하는 사례가 확인된다(예: NETBID 가이드의 `4321150101`=데스크톱 컴퓨터, 검색엔진에 색인된 `[4412163501]접착테이프커터` — 둘 다 10자리). 이는 RESEARCH.md의 8자리 설명과 모순되지 않는다 — **물품분류번호 자체는 8자리이고, 그 뒤에 개별 규격을 식별하는 물품식별번호 2자리가 추가로 붙는 구조**다. D-06이 조인 키로 삼는 것은 물품분류번호(최대 8자리, prefix 매칭 가능한 부분)이며, 물품식별번호까지 포함한 10자리 값은 이 프로젝트의 매칭 범위가 아니다.

## 미확인 항목과 확인 방법

**1. 시설관리 업종의 물품분류번호(또는 용역분류코드) 전체**
- (a) 조회 경로: `goods.g2b.go.kr:8053` 목록정보사이트 접속 → 검색창에 "시설관리", "시설물유지관리", "청소용역", "건물관리" 키워드로 각각 검색 → 결과 목록의 분류코드 컬럼 확인. 검색이 0건이면 "용역" 탭이 별도로 있는지, 또는 나라장터 용역 공고가 물품분류번호 없이 참가자격 업종코드만으로 공고되는지 화면상에서 직접 확인.
- (b) 누가 언제 확인하는가: Phase 2 착수 첫 주, DB 스키마 확정(플랜 03) 이전에 개발자(1인)가 직접 로그인 없이 접근 가능한 검색 화면에서 확인. 로그인이 필요하면 data.g2b.go.kr 계정으로 로그인 후 확인.
- (c) 틀렸을 때의 영향: 시설관리 업종을 등록한 업체에게 해당 분야 공고가 전혀 매칭되지 않는다 — 4개 목표 업종 중 하나가 처음부터 매칭 기능에서 빠지는 것과 같아, 초기 사용자 확보(D-08 취지)에 직접 타격을 준다.
- 근거: RESEARCH.md Assumptions Log A2("서비스(용역) 분류 체계가 물품분류번호와 동일 자릿수 구조를 따른다는 가정 — 용역은 별도 분류 체계를 쓸 가능성 있음").

**2. 정보통신·소프트웨어개발 행의 8자리 품명분류 예시(`43211501`, `43211502`, `43211817`)**

- 근거: Naver 색인 결과에서 `551015`(6자리)까지만 확인, 8자리 품명분류는 검색 결과에 노출되지 않음.

## 프로필 저장 형식 권장안

업체 프로필은 온보딩에서 **물품분류번호의 대분류(2자리) 또는 중분류(4자리) 단위를 다중 선택**하고, 저장 시에는 선택한 prefix 문자열을 그대로 보관하는 방식을 권장한다. 8자리 품명분류 단위의 강제 입력은 요구하지 않는다 — 이유는 두 가지다: (1) 중소 업체가 자사 취급 품목의 8자리 코드를 전부 알기 어렵고 입력 부담이 온보딩 이탈로 이어질 수 있다, (2) 너무 좁은 단위(8자리)로만 매칭을 걸면 리콜이 급감해 "받고 싶은 조달을 놓치지 않는다"는 핵심 가치와 충돌한다.

저장 값의 자릿수는 **2/4/6/8로 가변**이다 — 위 §목표 업종 매핑표에서도 사무용품(44, 2자리 대분류 확인)과 인쇄·출판(551015, 6자리 소분류 확인)의 확인 깊이가 서로 다른 것처럼, 업체마다 선택하는 정밀도가 다를 수 있다. 이것이 플랜 03의 `company_classification_codes` 테이블 컬럼 정의에 미치는 영향: RESEARCH.md 초안 스키마의 `classification_code VARCHAR(8)` 컬럼 타입 자체는 문제가 없다 — PostgreSQL `VARCHAR(n)`은 이미 가변 길이이므로 2/4/6/8자리 값을 그대로 저장할 수 있다. 다만 애플리케이션·쿼리 레벨에서 "저장된 값이 항상 8자리"라고 가정하면 안 되며, prefix 매칭(`LIKE company_code || '%'`)으로 다양한 자릿수를 다뤄야 한다.

## 매칭 규칙 (Phase 2 인계)

공고의 분류코드와 업체가 등록한 prefix를 대조하는 규칙은 다음을 최소 포함한다 — 단, 구체적 점수 수식은 이 문서에서 확정하지 않고 **Phase 2에서 확정**한다. 이 문서는 조인 키 설계 문서이지 스코어링 알고리즘 설계 문서가 아니다.

(a) **기본 규칙 — prefix 일치.** 공고의 분류코드(`bid_announcements.classification_code`)가 업체가 등록한 prefix(`company_classification_codes.classification_code`)로 시작하면 매칭 후보로 삼는다. 예: 업체가 `43`(대분류)만 등록했다면 `43211501`로 시작하는 모든 공고가 후보가 된다. 업체가 `4412`(중분류)까지 등록했다면 그보다 좁은 범위만 후보가 된다.

(b) **일치 자릿수와 적합도.** 일치하는 자릿수가 길수록(8 > 6 > 4 > 2) 적합도 점수를 높게 준다는 방향성만 이 문서에 남긴다 — 8자리 완전 일치가 가장 정밀한 매칭이고, 2자리(대분류)만 일치하면 폭넓지만 느슨한 매칭이다.

(c) **분류코드가 비어 있는 공고의 처리 방침.** 원문 파싱 실패 등으로 `classification_code`가 비어 있는 공고는 매칭 후보에서 완전히 제외하지 않고, 제목·본문 키워드 매칭으로 보조 판정 후보에 남긴다 — 분류코드 결측이 곧 "관련 없음"을 의미하지 않기 때문이다.

(d) **범위 경계.** 지역·실적·인증은 분류코드와 별개의 가중치 축이며, 이 문서의 범위가 아니다 — 스코어링 엔진(MATCH-01) 전체 설계는 Phase 2의 몫이다.

## 이번 Phase 범위 밖

다음 3가지는 이번 Phase에서 명시적으로 제외한다.

**(a) 통계청 표준산업분류(KSIC) ↔ 물품분류번호 이중 매핑 테이블.** `D-07`에 따라 이번 Phase에서 만들지 않는다. KSIC는 세무·통계 목적의 분류이며, 물품분류번호와 자동 변환해주는 공식 매핑 API가 확인되지 않았다(RESEARCH.md). 필요해지면 이후 Phase에서 별도 매핑 테이블로 추가한다.

**(b) 목표 4개 업종을 넘는 전체 분류체계 매핑.** `D-08`에 따라 목표 업종 3~5개(이 문서에서는 4개: 정보통신·소프트웨어개발/사무용품/시설관리/인쇄·출판)로 시작해 초기 사용자 확보에 집중한다. UNSPSC 전체 대분류(43개 세그먼트) 매핑은 이번 Phase의 범위가 아니다.

**(c) 나라장터 참가자격 업종코드 기반 자격 판별.** 업체가 특정 입찰에 실제로 참가할 자격이 있는지(면허·인증 요건 포함)를 판정하는 기능은 Phase 4(ELIG)의 범위다. 이 문서의 §세 가지 코드 체계 구분에서 "참고용 보조 필드"로 분류한 나라장터 업종코드(참가자격)는 그 Phase에서 다시 다룬다.
