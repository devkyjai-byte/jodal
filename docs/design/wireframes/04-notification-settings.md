# 화면: 알림 설정

**목적:** 업체가 매칭 알림을 받는 채널·강도·시간대를 직접 조정해 "필요한 만큼만" 알림을 받게 한다.
**진입 경로:** 온보딩 스텝 5의 "알림 설정 화면으로 이동" 링크, 공고 상세(`03-detail.md`)의 "이 업종 알림 조정하기" 액션, 전역 내비게이션의 설정 메뉴.

## 레이아웃

설정 항목을 그룹으로 나눠 배치하고, 각 항목의 입력 형태와 기본값을 함께 표시한다.

- **채널** — 이메일 on/off(토글, 기본값 on), 푸시 on/off(토글, 기본값 off). 푸시는 Phase 3 네이티브 전환 이전에는 브라우저 푸시 권한에 의존한다는 점을 항목 아래 작은 글씨로 표기한다(`MATCH-03`, 네이티브 푸시는 `CLIENT-04`로 Phase 3 범위).
- **적합도 임계값** — 슬라이더(5단계 정성 등급과 동일한 눈금: 매우 적합~참고용). "이 값 이상만 알림을 보냅니다"라는 의미와, "값을 올리면 알림이 줄고 원하는 공고를 놓칠 위험이 커집니다"라는 트레이드오프 안내를 슬라이더 아래 고정 문구로 둔다.
- **발송 빈도** — 즉시 / 일간 요약 중 단일 선택(라디오, 기본값 즉시).
- **방해금지 시간대** — 시작 시각·종료 시각 선택(타임피커, 기본값 없음/미설정).
- **마감임박 리마인더** — on/off 토글(기본값 on)과 "며칠 전" 선택(기본값 3일 전).
- **최근 발송 이력 보기** — 읽기 전용 링크. 클릭 시 최근 발송 목록(채널·발송 시각·상태)을 펼쳐 보여준다.
- **카카오 알림톡** — 이번 범위 밖임을 한 줄로 표기한다: "카카오 알림톡 연동은 추후 지원 예정입니다" (`NOTF-01`, v2 요구사항).

## 상호작용

- 이메일 토글 변경 → **변경 즉시 저장**된다(별도 저장 버튼 없음). 근거: 설정 화면은 항목이 서로 독립적이고 되돌리기 쉬운 토글/슬라이더 위주라, 저장 버튼을 두면 "저장을 눌러야 하나?"라는 불확실성만 늘어난다 — 변경 즉시 저장 후 화면 하단에 짧은 토스트("저장됨")로 피드백한다.
- 푸시 토글을 on으로 변경 → 브라우저의 알림 권한 요청 다이얼로그가 뜬다. 사용자가 허용하면 토글이 on으로 확정되고, 거부하면 토글이 다시 off로 되돌아가며 "브라우저 알림 권한이 필요합니다" 안내를 표시한다.
- 적합도 임계값 슬라이더 조정 → 조정 중 "이 값으로 설정하면 최근 7일 기준 약 N건의 알림을 받았을 거예요" 예상 알림량 안내를 실시간으로 갱신해 보여준다.
- 이메일·푸시를 모두 off로 만들려는 시도(마지막 채널을 끄는 순간) → 즉시 끄지 않고 "모든 알림을 끄면 새 공고를 놓칠 수 있습니다. 계속하시겠어요?" 확인 다이얼로그를 띄운다. 확인해야 최종 반영된다.
- "최근 발송 이력 보기" 클릭 → 목록이 펼쳐지며 채널·발송 시각·상태(성공/실패)를 표로 보여준다.
- 방해금지 시간대의 시작·종료 시각 입력 → 종료 시각이 시작 시각보다 빠르면(예: 다음날 새벽까지) 자정을 넘기는 구간으로 자동 해석해 저장한다.

## 데이터 소스

`notification_settings`를 읽고 쓴다. 최근 발송 이력은 `notification_logs`를 읽기 전용으로 조회한다. 이 화면의 모든 설정 항목은 매칭 알림 발송 조건(`MATCH-02`)과 발송 채널·빈도(`MATCH-03`)를 사용자가 직접 제어하는 통로이며, 저장 컬럼과 1:1로 연결되어야 Phase 2가 화면과 스키마를 따로 해석하지 않는다. 화면 항목과 저장 컬럼의 대응은 다음과 같다.

| 화면 항목 | 대응 컬럼 | 기본값 |
|---|---|---|
| 이메일 채널 on/off | `notification_settings.email_enabled` | `true` |
| 푸시 채널 on/off | `notification_settings.push_enabled` | `false` |
| 적합도 임계값 | `notification_settings.min_score_threshold` | 정성 등급 중간값(예: "적합" 등급 상당) |
| 발송 빈도 | `notification_settings.digest_frequency` | `'immediate'` |
| 방해금지 시작 시각 | `notification_settings.quiet_hours_start` | 미설정(NULL) |
| 방해금지 종료 시각 | `notification_settings.quiet_hours_end` | 미설정(NULL) |
| 마감임박 리마인더 on/off | `notification_settings.deadline_reminder_enabled` | `true` |
| 마감임박 리마인더 며칠 전 | `notification_settings.deadline_reminder_days` | `3` |

`docs/design/db-schema-design.md`(플랜 03 산출물)가 이미 존재하면 그 문서의 컬럼명을 우선 인용해야 한다 — 이 문서 작성 시점에는 플랜 03이 아직 완료되지 않아 위 컬럼명은 이 플랜이 잠정 제안한 값이며, 플랜 03의 실제 스키마와 차이가 있으면 그쪽을 따른다.

## 엣지 케이스

- **모든 채널을 끈 경우** — 이메일·푸시가 둘 다 off가 되면, "원하는 조달 공고를 놓치지 않는다"는 핵심 가치 자체가 성립하지 않게 되는 지점이다(`00-user-journey.md` §여정이 끊기는 지점). §상호작용에서 서술한 확인 다이얼로그로 막고, 확인 후에도 화면 상단에 "모든 알림이 꺼져 있습니다" 경고 배너를 지속 노출한다.
- **브라우저 푸시 권한 거부·차단** — 권한 요청이 거부되면 토글을 off로 되돌리고, 브라우저 설정에서 권한을 다시 허용하는 방법을 안내하는 링크를 제공한다.
- **이메일 반송 상태인 주소** — `notification_logs`에 연속 반송(bounce) 이력이 쌓이면 이메일 채널 항목 옆에 "발송 실패가 반복되고 있어요 — 이메일 주소를 확인해주세요" 경고를 표시한다.
- **방해금지 시간대에 발생한 알림의 처리 방침** — 버리지 않고 다음 발송 가능 시각까지 미룬다(방해금지 종료 시각 직후 일괄 발송). 근거: 조달 공고는 마감 기한이 있는 시간 민감 정보라, 알림을 완전히 버리면 사용자가 공고 자체를 놓칠 수 있다 — 핵심 가치와 직접 충돌한다.
- **설정 저장 실패** — 토글/슬라이더 변경 직후 저장 요청이 실패하면 UI를 이전 값으로 되돌리고 "저장하지 못했습니다. 다시 시도해주세요" 토스트를 표시한다(낙관적 업데이트 롤백).
