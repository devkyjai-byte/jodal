2. `## 핵심 여정 (한 사람, 한 경로)` — 분기 없는 단 하나의 경로를 4단계로 서술한다. 시나리오: 정보통신 업종의 소규모 업체 담당자 1명이 처음 가입해 첫 매칭 알림을 받고 그 공고를 확인한 뒤 알림 강도를 조정한다.
   - 단계는 순서대로 ① 가입·업체 프로필 등록(업종 대분류 1개, 지역 1개 선택, 실적·인증은 건너뜀) → ② 첫 매칭 이메일 알림 수신 → ③ 알림 링크로 공고 상세 진입, 나라장터 원문으로 대조 → ④ 알림이 너무 많다고 느껴 적합도 임계값을 올림.
   - 각 단계마다 다음 4요소를 빠짐없이 적는다: (화면 / 사용자 행동 / 시스템 반응 / 다음 단계로 넘기는 값).
   - 분기·예외·에러는 여기서 다루지 않고 각 화면 문서의 §엣지 케이스로 미룬다는 점을 섹션 끝에 한 줄로 밝힌다.

3. `## 화면 간 데이터 인계 계약` — 표. 컬럼: 출발 지점 / 도착 화면 / 넘기는 값 / 도착 화면이 그 값으로 무엇을 조회하는가. 최소 4행을 채운다: 온보딩 → 피드(등록된 업종 prefix·지역), 이메일 알림 → 상세(공고 식별자·매칭 식별자), 피드 → 상세(공고 식별자), 상세 → 알림 설정(어떤 알림이 과했는지 맥락). 각 행의 "넘기는 값"에는 URL 파라미터로 노출되는 값과 서버가 세션에서 꺼내는 값을 구분해 적는다.

4. `## 화면별 읽기·쓰기 테이블` — 표. 컬럼: 화면 / 읽는 테이블 / 쓰는 테이블 / 관련 요구사항 ID. 4화면 각각 1행.
   표준 테이블 이름은 다음을 사용한다: `companies`, `company_classification_codes`, `company_performances`, `company_certifications`, `bid_announcements`, `matches`, `notification_logs`, `notification_settings`.
   `docs/design/db-schema-design.md`(플랜 03 산출물)가 이미 존재하면 그 문서의 테이블·컬럼명을 우선해 인용하고, 위 목록과 차이가 있으면 표 아래 각주로 남긴다. 존재하지 않으면 위 목록을 그대로 쓴다 — 플랜 03 이 같은 목록으로 작성한다.

5. `## 여정이 끊기는 지점` — 이 경로가 실패하는 지점 3가지와, 어느 화면이 그것을 어떻게 처리해야 하는지를 한 줄씩 적는다. 최소 다음 3개를 포함한다: 프로필은 등록했는데 매칭 결과가 0건인 경우, 알림 링크로 들어온 공고가 이미 마감됐거나 개정된 경우, 사용자가 모든 알림 채널을 끈 경우(핵심 가치가 성립하지 않게 되는 지점). 각 항목에 담당 화면 파일명을 적어 화면 문서로 연결한다.
