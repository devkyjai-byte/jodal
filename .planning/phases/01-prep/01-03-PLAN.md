1. `## 결론 먼저` — 5줄 내외. 이 스키마가 답하는 질문("어떤 업체에게 어떤 공고를 왜 보여줄 것인가")을 한 문장으로 적고, 설계 대상 테이블을 4개 도메인으로 묶어 나열한다: 업체 프로필군 / 공고 / 매칭 / 알림. D-04 를 근거로 인용하고, Phase 4~6 전용 테이블은 D-05 에 따라 이 문서에서 설계하지 않는다는 경계를 한 줄로 선언한다. 저장 스택은 PostgreSQL 이며 UUID 기본키·TIMESTAMPTZ·JSONB 관례를 따른다는 것도 한 줄로 밝힌다.

2. `## 데이터 흐름 스파인` — 이 문서의 척추. **분기 없는 단 하나의 경로**를 5단계로 서술한다. 시나리오: 업체 A 가 온보딩에서 대분류 `43` 하나만 선택했고, Ingestion 배치가 분류코드 `43211501` 인 공고 1건을 수집했으며, 그 결과 업체 A 에게 이메일 알림 1건이 나간다.
   - 단계별로 (a) 어느 테이블에 무슨 행이 생기는가, (b) 어느 컬럼이 읽히는가, (c) 어느 키로 다음 단계와 연결되는가 — 이 세 가지를 빠짐없이 적는다.
   - 5단계는 순서대로: ① 업체 등록 → `companies` 1행 + `company_classification_codes` 1행(값 `43`), ② 공고 수집 → `bid_announcements` 1행(분류코드 `43211501`, 원문 payload 보관), ③ prefix 대조로 매칭 → `matches` 1행(점수·매칭 시각), ④ 발송 여부 판단 → `notification_settings` 에서 채널 on/off 와 적합도 임계값 확인, ⑤ 발송 기록 → `notification_logs` 1행(채널·상태·시각).
   - 이 섹션 안에 **조인 SQL 한 개**를 SQL 코드블록으로 싣는다: 아직 알림이 나가지 않은 (업체, 공고) 후보를 뽑는 SELECT 로, `companies` → `company_classification_codes` → `bid_announcements`(prefix 대조) → `matches` → `notification_logs`(미발송 조건) 를 모두 통과해야 하며 `JOIN` 과 prefix 대조를 위한 `LIKE` 를 실제로 사용한다. 모든 조회가 `company_id` 로 스코프된다는 점이 SQL 에서 드러나게 쓴다.
   - 마지막에 `docs/design/업종-물품분류-매핑.md` 를 파일명 그대로 인용해, 이 스파인의 prefix 대조 규칙이 그 문서 §매칭 규칙에서 왔음을 밝힌다.

3. `## 스파인이 강제하는 설계 제약` — 위 경로를 실제로 성립시키기 위해 스키마가 반드시 만족해야 하는 제약 4가지를 각각 (결정 / 근거 / 어기면 무슨 일이 일어나는가) 형식으로 적는다.
   - (a) **분류코드 컬럼은 고정 8자리가 아니다.** 업체가 저장하는 값의 자릿수는 2/4/6/8 로 가변이다. `VARCHAR(8)` 타입 자체는 이미 가변 길이라 문제가 없지만, 애플리케이션·쿼리가 "항상 8자리"를 가정하면 안 된다. 허용 자릿수 집합을 SQL `CHECK` 제약으로 못 박고(허용 길이를 `2, 4, 6, 8` 로 열거), 숫자만 허용하는 패턴 제약도 함께 건다. 근거는 `docs/design/업종-물품분류-매핑.md` §프로필 저장 형식 권장안.
   - (b) **prefix 매칭을 인덱스로 지원하는 방법을 최소 2가지 제시하고 하나를 권장안으로 고른다.** 최소 다음 두 가지를 비교한다: (i) 공고 쪽 분류코드에 `varchar_pattern_ops` 계열 btree 인덱스를 걸고 리터럴 prefix 로 범위 스캔하는 방법, (ii) 공고 분류코드를 2/4/6/8 자리 prefix 로 전개해 업체 저장 값과 등가 조인하는 방법. 각각의 장점·한계(특히 업체 행마다 패턴이 달라지는 조인 형태에서 인덱스가 쓰이는지)를 적고, 권장안과 그 근거를 단정적으로 밝힌 뒤 실측 검증은 Phase 2 의 몫으로 남긴다.
   - (c) **분류코드가 비어 있는 공고를 후보에서 배제하지 않는다.** 매핑 문서 §매칭 규칙 (c) 에 따라 공고 쪽 분류코드는 NULL 을 허용하고, NULL 공고를 제목·본문 키워드 경로로 넘기는 방침을 한 줄로 적는다. 스파인 SQL 이 이 경로를 다루지 않는다는 점(스파인은 단일 happy path)도 함께 밝힌다.
   - (d) **같은 매칭에 같은 채널로 알림이 두 번 나가지 않는다.** 발송 이력 테이블에 `UNIQUE (match_id, channel)` 을 두어 배치 재시도·중복 실행이 사용자에게 같은 알림을 반복 발송하는 것을 스키마 레벨에서 차단한다. 재시도 시 상태 컬럼을 갱신하는 방식(행 추가가 아니라 갱신)이라는 점을 한 줄로 적는다.

7. `## 민감정보 저장 규칙` — 사업자등록번호를 중심으로 저장 규칙을 확정한다. 다음을 모두 담는다.
   - **평문 컬럼을 두지 않는다.** 대신 두 컬럼으로 분리 저장한다: 암호문을 담는 `BYTEA` 컬럼과, 중복 가입 판정·조회에 쓰는 고정 길이 다이제스트 컬럼. 다이제스트 컬럼에 유일 인덱스를 걸어 중복 가입을 막는다.
   - **왜 단순 해시가 아니라 서버 비밀을 섞은 `HMAC` 인가.** 사업자등록번호는 10자리 숫자라 전체 값 공간을 전수 열거할 수 있다. 서버 비밀(pepper) 없이 해시만 저장하면 유출 시 사실상 평문과 같다는 점을 근거로 명시한다.
   - **암호화 수단.** PostgreSQL `pgcrypto` 또는 애플리케이션 레벨의 검증된 AEAD 라이브러리 중 하나를 쓰고, 자체 암호 알고리즘 구현은 금지한다(RESEARCH.md §Don't Hand-Roll). 두 방식의 선택 기준(키를 DB 가 보느냐 앱만 보느냐)을 한 줄씩 비교하고 최종 선택은 Phase 2 로 위임한다.
   - **키·pepper 관리.** 암호화 키와 pepper 는 환경변수 또는 시크릿 매니저에만 두고 이 문서를 포함한 어떤 git 산출물에도 실제 값을 적지 않는다 — `docs/design/api-신청-체크리스트.md` §서비스키 보관 규칙과 같은 관례임을 밝힌다. 예시 자리에는 자리표시자만 쓴다.
   - **진위확인(PROF-05).** 국세청 사업자등록정보 진위확인 API 를 쓰되, 응답 원문 전체를 보관하지 않고 판정 결과 상태와 확인 시각만 컬럼으로 남긴다는 방침을 적는다.
